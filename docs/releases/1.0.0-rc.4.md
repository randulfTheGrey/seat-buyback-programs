# Buyback Programs 1.0.0-rc.4

`1.0.0-rc.4` is the targeted permission-namespace compatibility release before
stable `1.0.0`. It replaces the generic SeAT ACL scope with the package vendor
scope to avoid collisions with other plugins:

| Previous RC identifier | RC4 identifier |
| --- | --- |
| `buyback.request` | `randulfthegrey-buyback.request` |
| `buyback.manage` | `randulfthegrey-buyback.manage` |
| `buyback.admin` | `randulfthegrey-buyback.admin` |

The three abilities and their independence are unchanged. No legacy alias is
registered. This is a breaking prerelease authorization-identifier change.

## Upgrade behavior

This release deliberately includes no ACL data migration. Another plugin may
own the same `buyback.*` permission titles, while SeAT's ACL records contain no
package ownership information. Automatically renaming, copying, merging, or
deleting those rows could change the other plugin's access.

Before updating, record every role that holds an old permission. Back up the
database and Composer state, enter maintenance mode, update the package, and run
the standard package migrations and discovery steps. Through normal SeAT role
management, add the corresponding `randulfthegrey-buyback.*` grant to each
intended role. Leave all existing `buyback.*` rows and grants untouched for the
other plugin.

Until the new grants are applied, Buyback Programs access fails closed. After
the manual remapping, run:

```bash
php artisan cache:clear redis
php artisan optimize:clear
```

Restart Horizon and every queue worker before completing validation. The Redis
clear covers entity-scoped SeAT ACL cache keys and also removes transient
appraisal cache entries; persisted Quotes and Requests are unaffected.

The standard SeAT `PluginDatabaseSeeder` is not a permission synchronizer and
does not create the new grants. Update external role-provisioning scripts,
deployment checks, documentation, or automation that names the old permissions.

## Rollback

There is no ACL migration to reverse. The old permission records remain
available if the package code is rolled back. New vendor-prefixed permission
rows may remain unused; remove them only after validating the rollback and
confirming no installed package consumes them. Prefer restoring the database
backup together with the matching Composer state for a complete rollback, then
clear caches and restart workers.

After the upgrade, verify requester, manager, and administrator access
independently and run the appraisal → Quote → Request → terminal-action smoke
path. This document prepares the candidate; it does not publish, tag, or release
it.
